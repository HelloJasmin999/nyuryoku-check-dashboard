# 本番DBを変更する時の安全な段取りチェックリスト

## 通常の段取り（データが本当に永続化されている場合）

- [ ] 変更前に本番DBのバックアップを取った
- [ ] マイグレーションをstaging環境で先に実行し、動作確認した
- [ ] 既存データの件数・内容が変更前後で変わっていないことを確認した
- [ ] 既存のテスト（`python -m pytest tests/`）がstagingで通ることを確認した
- [ ] 問題なければ本番にも同じマイグレーションを適用した
- [ ] 本番適用後、バックアップから復元できることを（可能なら）確認済み

## nyuryoku-check-dashboard固有の注意点（第14回で判明）

- [ ] **本番（Render無料プラン）はファイルシステムが一時的**。`cases.db`は再デプロイ・再起動のたびにリセットされ、`init_db()`で毎回作り直される。「本番DBのバックアップ」は今のところ実質的な意味を持たない。
- [ ] 列を追加・変更する場合は、`scripts/migrate_add_memo_column.py`のような単発マイグレーションだけでなく、**`server.py`の`init_db()`内の`CREATE TABLE`定義自体も同時に更新する**（そうしないと再デプロイ後の新しいDBに新列が反映されない）。
- [ ] 将来、本物の患者データなど「本当に消えたら困るデータ」を扱うようになったら、その前に**Renderの永続ディスク（有料プラン）またはRender Postgresなど、データが実際に永続化される構成に切り替える**ことが必須（今の構成のまま本番運用してはいけない）。

### 実証済み（2026-08-26）

PR #17を本番masterへマージ後、実際の本番URL（`nyuryoku-check-dashboard-1.onrender.com`）を確認したところ、`seed_demo_data()`（[server.py:66-73](../server.py)）が生成する6件（患者A〜F、`today()`基準の日付）とデータが完全一致していた。ローカルの練習用`cases.db`（7件、患者Gまで含む・別日付）とは全く別物であることも確認済み。**理論上の懸念で終わらせず、本番デプロイのたびにDBが作り直されることを実際に確認できた。**

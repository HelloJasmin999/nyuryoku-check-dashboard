## 設計判断の一言

一番悩んだのは「メール送信をどうするか」。本物のメールサーバーを用意すると今回のコースの範囲を超えてしまうため、確認リンク・再設定リンクを画面にそのまま表示する「デモ用の疑似メール確認」にした。ただし、本番化する時に困らないよう、リンクを作る部分と実際に送信する部分を分けて実装した。もう一つの判断は、ロールの割り当て方。「そのクリニックで最初に登録した人が自動的に管理者」というシンプルなルールにして、招待の仕組みは今回のスコープ外にした。

## 動作確認

ブラウザで実際に一連の流れを確認：

1. `/signup`で「さくらクリニック」を選び1人目を登録 → 表示された確認リンクをクリック → ログイン成功 → 「管理者」バッジが表示され、案件追加フォームが見える。
2. 実際に案件を1件追加できることを確認。
3. 同じ「さくらクリニック」で2人目を登録・確認・ログイン → 「一般ユーザー」バッジが表示され、案件追加フォームの代わりに「案件の追加は管理者のみ行えます」と表示される。
4. 一般ユーザーのセッションのまま`POST /api/cases`を直接叩いても`403`で拒否されることを確認（UI側で隠しているだけでなく、サーバー側でも権限チェックしていることの確認）。
5. パスワード再発行：`/forgot-password`でメール送信→表示されたリンクから新しいパスワードを設定→ログイン画面に「パスワードを再設定しました」と表示→新パスワードでログイン成功。
6. 自動テスト11本、全てPASS（`python -m pytest`）。
7. staging環境（デプロイ済みサイト）でも実際に新規登録〜ログイン〜権限による画面の違いを確認済み。

## ふりかえり

第16回では「データを分ける」箱（tenant_id）は作ったが、「誰がその箱を開けていいか」を保証する鍵が無かった、という繋がりがはっきり見えた回だった。ロールを実装してみて、「見えるものを変える」（UI側で隠す）だけでは不十分で、「できる操作そのものをサーバー側で拒否する」ところまでやって初めて権限と呼べる、ということを実際に403エラーを確認して実感した。

# マイグレーションの記録（第14回：本番DBを壊さず育てる）

## お題

`cases`テーブルに新しい列（`memo`＝担当者メモ用）を、既存データを壊さずに追加する。

## やったこと

1. まず[backup_db.py](../scripts/backup_db.py)でローカルの`cases.db`をバックアップ（`backups/cases_20260826_161844.db`）。
2. [migrate_add_memo_column.py](../scripts/migrate_add_memo_column.py)を実行し、`memo`列を追加。
   - `PRAGMA table_info`で列の存在を先にチェックしてから`ALTER TABLE`する作りにした（2回実行しても壊れない＝冪等）。
3. 移行前後で件数（7件）が変わっていないこと、既存の`patient_label`等のデータがそのまま残っていることを確認。
4. `server.py`の`init_db()`も同様に更新した。理由は下記「設計判断の一言」を参照。
5. `python -m pytest tests/`が引き続き2件パスすることを確認。

## 検証結果

| 項目 | 移行前 | 移行後 |
|---|---|---|
| カラム | id, patient_label, doctor_name, surgery_date, item, status, created_at, resolved_at | 上記 + memo |
| 件数 | 7件 | 7件（変化なし） |
| 既存データ | 患者A〜Gの内容そのまま | 変化なし（memoはNULL） |

## 設計判断の一言

**このアプリはRender無料プランで動いており、Webサービスのファイルシステムは一時的（再デプロイ・再起動のたびにリセットされる）。つまり本番の`cases.db`は毎回`init_db()`によってゼロから作り直されている。**

そのため、「既存の本番DBに対して`ALTER TABLE`を実行する」という一般的なマイグレーション作業は、今の構成では実質的に発生しない（次にデプロイした瞬間、新しい空のDBが`CREATE TABLE`から作られるため）。

これを踏まえて、`init_db()`の`CREATE TABLE`文自体に最初から`memo`列を含めた上で、**もし将来「本当に既存データが残ったまま起動するケース」（有料プランの永続ディスク、またはPostgresなど）に切り替わっても安全なように**、`ALTER TABLE`による追従処理（`column_exists`チェック→無ければ追加）もあえて残した。

つまり今回のマイグレーションは「今すぐ本番で必要」というより、「将来データが本当に永続化されたときに、いきなり壊れないための保険」として実装した。

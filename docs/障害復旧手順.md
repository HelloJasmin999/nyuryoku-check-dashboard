# 障害復旧の型（第15回：本番運用の総合演習）

「落ちた」と気づいてから、元に戻すまでの動き方を1枚にした型。
前提：本番=`master`ブランチ→Renderの本番サービス、検証=`staging`ブランチ→Renderのstaging用サービス（[リリース手順.md](../リリース手順.md)と対になる資料）。

## 全体の流れ（4ステップ）

```
① 気づく → ② 切り分け → ③ ロールバック → ④ 復旧確認
```

## ① 気づく

- UptimeRobot（第15回で導入）が本番URLを5分おきに監視し、繋がらなくなったらメール通知が来る。
- 自分で気づく前に通知が来る状態にしてあるので、「利用者から連絡が来て初めて気づく」を防ぐのが目的。

## ② 切り分け（原因はどっち？）

| 症状 | 疑う原因 | 確認する場所 |
|---|---|---|
| 本番URLにアクセスできない（真っ白・タイムアウト） | Render側の障害 or 直前のデプロイでコードが壊れた | Renderダッシュボードの「Events」「Logs」タブでエラー内容を確認 |
| アクセスはできるが、画面や動作がおかしい | 直前にmasterへ入れた変更が原因の可能性が高い | GitHubのコミット履歴で直近の変更内容を確認 |
| 数十秒待つと直る | 無料プランのスリープからの復帰（障害ではない） | もう一度アクセスして直るか確認してから次に進む |

**まずログを見る。ログにエラーが出ていれば「コードが原因」、ログに何も出ずRender自体が応答しないなら「基盤側の問題」の可能性が高い。**

## ③ ロールバック（2つのやり方）

### 方法A：Renderダッシュボードから1つ前のデプロイに戻す（最速）

1. Renderダッシュボード → 本番サービス → 「Events」タブ
2. 正常に動いていた頃のデプロイを選び、「Redeploy」
3. 数十秒〜数分で切り替わる

→ **一番早いが、GitHub側の履歴（コード）はそのまま**。次に誰かがmasterからデプロイし直すと、また同じ壊れたコードが出てしまう点に注意。

### 方法B：git revertで正式に戻す（[リリース手順.md](../リリース手順.md)と同じ流れ）

1. 原因のコミットを`git revert`で打ち消す
2. `staging`へpush → PRでCI（pytest）が緑になることを確認 → マージ
3. staging用URLで直っていることを確認
4. `staging` → `master`のPRを作成・マージ（レビュー必須はオーナー権限でbypass）
5. 本番へ自動デプロイされる

→ 時間はAより掛かるが、**GitHub上の履歴も正しい状態に戻る**ので、後から見た人が混乱しない。

**使い分け：まずAで応急処置し、落ち着いたらBで正式に直す、の合わせ技が現実的。**

## ④ 復旧確認

- 本番URLをPC・スマホ両方で開き、直っているか確認
- UptimeRobotのステータスが「Up」に戻っているか確認
- （データを扱うようになった場合）[バックアップ復元手順.md](./バックアップ復元手順.md)に沿ってデータの整合性も確認

## このアプリ固有の注意点

- Render無料プランは**ファイルシステムが一時的**なので、`cases.db`は再デプロイのたびにサンプルデータへリセットされる（[DB変更チェックリスト.md](./DB変更チェックリスト.md)参照）。つまり今の構成では「データが壊れて戻せない」事故は起きない。壊れるとしたら常に**コード側**。
- 無料プランは無操作でスリープするため、「本当に落ちた」のか「スリープから起きている最中」なのかを②で必ず見極めてから③に進む（数十秒待って直るなら障害ではない）。

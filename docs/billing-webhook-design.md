# 課金②：継続課金を正しく回す（Webhook／第19回）

## ① これまでとの接続

[第18回（課金①）](billing-design.md)で、Stripeテストモードでの決済（チェックアウト→`/billing/success`で問い合わせて確定）を実装した。その設計判断で「Webhookが必要な継続課金の運用（請求失敗・解約の検知）は次回に回す」と明記していた通り、今回はその宿題に着手する。

## ② 今回のスコープ判断：3ステップのうち「解約→停止」の1本だけに絞った

課題文では①Webhook受信 ②状態自動切替（支払い失敗の猶予込み） ③解約フロー、の3ステップが指示されていたが、非エンジニアの自分にはWebhookの署名検証がそもそもイメージしづらく、欲張って全部やると「動くけど中身を説明できない」状態になりそうだった。課題文にあった「詰まったら、まず『解約されたら停止』の1本だけ、確実に動かす」という案内に従い、あえてスコープを絞った。

## ③ 実装した要素

| 要素 | 実装 |
|---|---|
| Webhook受信口 | `/webhooks/stripe`（POST）。ログイン不要（Stripeのサーバーから直接呼ばれるため） |
| 署名検証 | `stripe.Webhook.construct_event()`で`Stripe-Signature`ヘッダを検証。不正な署名は400で拒否 |
| 解約イベントの処理 | `customer.subscription.deleted`イベントを受け取ったら、`stripe_subscription_id`が一致するテナントの`plan`を`free`に更新 |
| 未対応イベントの扱い | それ以外のイベント種類は200を返すだけで何もしない（Stripeに同じ通知を再送させないため） |
| 環境変数 | `STRIPE_WEBHOOK_SECRET`を新設。未設定時は処理せずエラーを返す |

## ④ 設計判断：即時停止 vs 期間終了まで待つ

`customer.subscription.deleted`イベントは「サブスクが実際に終了した」タイミングで届く（即時解約・期間終了時解約のどちらの設定でも、最終的にこのイベントで通知される）。そのため、届いたら即座に`free`にするシンプルな実装にした。「解約はしたが契約期間の終了まで使わせる」という緩和ルールは、今回は意図的にスコープ外にした。

## ⑤ 設計判断：支払い失敗・猶予は対象外

課題本文にあった「支払い失敗時、猶予期間を置いてから停止」は今回実装していない。実装するなら`invoice.payment_failed`イベントを受け、失敗回数や猶予日数をテナントごとに記録して判定する仕組みが必要になり、難易度が上がるため次回以降に持ち越した。

## ⑥ セキュリティ上のポイント

- `Stripe-Signature`ヘッダの検証を必須にした。誰でもPOSTできるURLだが、「本物のStripeから来た通知か」を毎回確認してから処理する
- `STRIPE_WEBHOOK_SECRET`未設定時は黙って無視するのではなく、エラーを返して気づけるようにした
- テナントの特定は`stripe_subscription_id`の完全一致のみで行い、一致するテナントが無ければ何もしない（存在しないIDが来てもクラッシュしない）

## ⑦ 今後の注意点（次回以降への申し送り）

- 支払い失敗（`invoice.payment_failed`）の猶予処理は未実装
- 「解約したが契約期間の終了まで使える」という緩和は未実装（即時停止のみ）
- 本番（Render）にはまだ`STRIPE_WEBHOOK_SECRET`を登録しておらず、StripeダッシュボードでのWebhookエンドポイント登録もこれから

# 認証基盤の設計（第17回・SaaS本体編）

## ① これまでの回との接続

第16回（マルチテナント分離）で「クリニックごとにデータを分ける」仕組み自体は作ったが、当時は「今どのクリニックとしてアクセスしているか」を画面上部のプルダウン（`X-Clinic-Id`ヘッダ）で利用者に自己申告させているだけだった。誰でも他院になりすませる状態だったため、今回はここに本物の鍵（ログイン）をつけ、`tenant_id`の取得元をヘッダから「ログインセッション」に置き換えた。

## ② 実装した5つの要素

| 要素 | 実装 |
|---|---|
| サインアップ（メール確認） | `/signup` → `/api/signup`。所属クリニックを選び、メール＋パスワードで登録。未確認の間はログイン不可。 |
| ログイン／ログアウト・セッション | `/login` → `/api/login`。成功したらFlaskのセッションcookieに`user_id`を保存。`/api/logout`でセッション破棄。 |
| パスワード再発行 | `/forgot-password` → `/api/forgot-password`（トークン発行、1時間有効）→ `/reset-password/<token>`で新パスワード設定。 |
| ロール（権限） | `users.role`（`admin`/`staff`）。**そのクリニックで最初に登録した人が自動的に管理者、2人目以降は一般ユーザー**というシンプルな方式。 |
| （発展）SSO・ソーシャルログイン | 今回は対象外（将来の拡張候補として記録のみ）。 |

## ③ 設計判断：メール送信をどうするか

本物のメール送信には外部サービス（SMTPやSendGrid等）の契約・鍵設定が必要で、今回のコース内デモの範囲を超える。そこで、確認リンク・パスワード再設定リンクは**画面上に直接表示する**方式にした（「【デモ用】本来はメールで送信されるリンクです」と明記）。本番化する際は、この「リンクを表示する」部分を「メール送信APIを呼ぶ」処理に差し替えるだけで済むよう、リンク生成とトークン検証のロジックはメール送信手段と切り離して実装してある。

## ④ 設計判断：ロールの割り当て方

招待コードや管理者による招待の仕組みを作ると規模が大きくなりすぎるため、今回は「そのクリニックで最初に登録した人＝開設者＝管理者」という現実的な割り当てにした。管理者のみ「案件を追加する」操作ができ、一般ユーザーは閲覧と「確認済みにする」操作のみ行える（医療事務の実務に寄せて、案件の登録は管理側、日々の確認作業は一般ユーザー側、という役割分担）。

## ⑤ セキュリティ上のポイント

- パスワードは`werkzeug.security.generate_password_hash`でハッシュ化して保存。平文は一切保存しない。
- ログイン失敗時は「メールアドレスまたはパスワードが違います」という同じメッセージにし、どちらが間違っているか外部から推測されないようにした。
- パスワード再発行も、メールアドレスが未登録の場合と登録済みの場合で応答を変えず、アカウントの存在を外部から探れないようにした。
- `tenant_id`は必ずログイン中のユーザー自身の所属先から取得し、リクエスト側からの自己申告（ヘッダ等）は一切受け付けない（第16回時点の弱点を解消）。
- 案件の追加API（`POST /api/cases`）は管理者のみ実行可能で、これはUI側で隠すだけでなくサーバー側でも403で拒否することを確認済み（UIを迂回してAPIを直接叩いても防げる）。
- `SECRET_KEY`は環境変数から読み込む設計（本番ではRenderのVariablesに登録する必要あり。未設定時は開発用の一時キーで動作し、警告ログを出す）。

## ⑥ 今後の注意点（次回以降への申し送り）

- 本番で実際に使うには、確認リンク・再設定リンクの「画面表示」を「本物のメール送信」に差し替える必要がある。
- 現状はCSRFトークンによる保護までは入れていない（同一オリジンのfetch通信のみ・セッションcookieはHttpOnly）。本格的な決済等を扱う次回（課金編）までにはCSRF対策も検討する。
- スタッフの追加は今のところ「本人が自分で新規登録する」方式のみ。管理者がスタッフを招待する仕組みは未実装（将来の拡張候補）。

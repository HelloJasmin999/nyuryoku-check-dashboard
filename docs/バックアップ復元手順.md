# バックアップ／復元手順（第14回：本番DBを壊さず育てる）

## 先に大事な結論

**今のRender無料プラン構成では、本番の`cases.db`をバックアップしても意味がない。**
理由：Render無料プランのWebサービスはファイルシステムが一時的で、再デプロイ・再起動・スリープ復帰のたびにローカルファイルは消え、`init_db()`によって毎回サンプルデータから作り直される（[Render公式ドキュメント](https://render.com/docs/free)より）。つまり今の本番には「消えたら困る実データ」がそもそも存在しない。

→ 以下の手順は、**将来Renderの有料プラン（永続ディスク）や実データを扱うようになったときに使う手順**として用意した。今のうちにやり方を体験・記録しておく。

## バックアップ手順

```bash
python scripts/backup_db.py
```

- `backups/cases_YYYYMMDD_HHMMSS.db`という名前でタイムスタンプ付きコピーが作られる。
- `backups/`は`.gitignore`済み（実データが入り得るため、GitHubには上げない）。

### 実行結果（ローカルで確認済み）

```
バックアップ完了: backups/cases_20260826_161844.db
```

## 復元手順

1. アプリを止める（本番ならデプロイを一時停止、ローカルならサーバープロセスを止める）。
2. 戻したいタイムスタンプのバックアップファイルを`cases.db`という名前で元の場所に上書きコピーする。
   ```bash
   cp backups/cases_20260826_161844.db cases.db
   ```
3. アプリを再起動し、件数・内容が想定通りに戻っているか確認する。

### 復元の検証（今回実施）

実際に`cases.db`を上書きする代わりに、バックアップファイルの中身を直接調べて「正しい状態が保存されているか」を確認した（本番相当のファイルを不用意に壊さないため）。

- バックアップファイル（移行前の状態）：列は`memo`なし、件数7件
- 現在の`cases.db`（移行後）：列は`memo`あり、件数7件（データはそのまま）

→ バックアップには移行前の正しいスキーマとデータが保存されており、いざという時にこのファイルへ戻せば元の状態に復元できることを確認した。

## 定期バックアップ化する場合（将来やるなら）

- 有料プランで永続ディスクを使うようになったら、`scripts/backup_db.py`をRenderのCron Jobまたは外部のスケジューラ（GitHub Actionsの`schedule`トリガー等）から定期実行し、バックアップ先はサーバー内ではなく別のストレージ（S3等）に置く。
- 「バックアップが本当に取れているか」を月1回など定期的に開いて確認する運用も忘れずに（バックアップは"取れているつもり"が一番怖い）。

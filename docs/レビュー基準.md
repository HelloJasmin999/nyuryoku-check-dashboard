# PRレビュー基準（第11回：mainを仕組みで守る）

このリポジトリ（nyuryoku-check-dashboard）で、これからPRをレビューするときに使う基準とコメントの型。

## 何を見るか（チェックリスト）

| 観点 | 具体的に見ること |
|---|---|
| ①動くか | ローカル/staging環境で実際に動かして確認したか（説明文だけで判断しない） |
| ②漏れがないか | 空欄・文字数超過・連打・通信エラーなど、いじわる入力に耐えるか（第25回で発見した観点） |
| ③秘密情報が入っていないか | APIキー・パスワード・`.env`の中身がコードに直書きされていないか（第6回で確認した観点） |
| ④読みやすいか | 変更差分（diff）が、目的に対して過不足ないか。関係ない変更が紛れ込んでいないか |
| ⑤コミットメッセージ | `feat:` `fix:` `docs:` などの型が付いているか（第9回のコミットメッセージ規約に沿っているか） |
| ⑥ドキュメント | 手順や仕様が変わったなら、README・リリース手順.mdなどが一緒に更新されているか |

## 建設的コメントの書き方（詰問しない）

**型：良い点（Good）＋提案（Suggestion）の2点セットで書く。**

```
👍 Good: （具体的に良かった点。何がどう良いかまで書く）
💡 Suggestion: （改善案。命令形ではなく提案・質問の形で書く）
```

### 例①（今回のバッジ不具合を題材に）

- ❌ 詰問調：「これ本番にバッジ出ちゃってますよ、確認しました？」
- ✅ 良い例：
  ```
  👍 Good: RAILWAY_ENVIRONMENT_NAME で環境を判定する発想、Railway側の仕組みをそのまま使えていて良いですね。
  💡 Suggestion: 本番URLで見ると「検証環境」バッジが出たままでした。判定条件を staging === true 側だけに絞るとどうでしょう？
  ```

### 例②（コミットメッセージが型なしの場合）

- ✅ 良い例：
  ```
  👍 Good: 変更内容自体は必要十分で、動作確認もできています。
  💡 Suggestion: コミットメッセージに `fix:` を付けると、後から履歴を読む人が「バグ修正」と一目で分かるようになります（docs/コミットメッセージ規約.md参照）。
  ```

## 設計判断の一言

観点①〜⑥は、思いつきではなく、これまでの回で実際に自分がつまずいた・直した経験（第6回=秘密情報、第9回=コミット規約、第25回=いじわる入力）をそのままチェックリスト化したもの。レビューする側になっても、自分がユーザーとして踏んだ地雷を思い出せるようにしている。コメントを「Good＋Suggestion」の2点セット固定にしたのは、指摘だけだと出す側が萎縮し、PRを出すこと自体が怖くなってしまうため。
